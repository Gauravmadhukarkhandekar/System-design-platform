# Query Optimization

**Query optimization** is how you make **database work** cheaper: fewer rows touched, **indexes** used, less data over the wire, and **plans** that match your **filters** and **JOIN** patterns. Most gains come from **measuring** (EXPLAIN, timings) and then **changing** schema, indexes, or SQL — not from vague tuning knobs.

## EXPLAIN your queries

**EXPLAIN** (and **EXPLAIN ANALYZE** where supported) shows the **planned** or **actual** execution steps. Use it on **every slow or suspicious** query before guessing.

  title="What to look for (first pass)"

  rows={[
    [

    ],

    ],
    [

    ],
  ]}
/>

```sql
-- Postgres-style: planned nodes + actual timings
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, email FROM users WHERE email = 'alice@example.com';
```

<Callout variant="tip" title="Dialect differences">
Syntax varies: **Postgres** uses `EXPLAIN ANALYZE`; **MySQL** uses `EXPLAIN` / `EXPLAIN ANALYZE` in newer versions; **SQL Server** has `SET STATISTICS` and graphical plans. The **ideas** (scan vs seek, cost, rows) transfer across engines.
</Callout>

## Key optimization techniques

### Add proper indexes

Index columns that appear in **WHERE**, **JOIN** keys, and **ORDER BY**. Use **composite** indexes when filters combine columns (left-prefix rules still apply).

```sql
-- Bad: selective filter with no supporting index (planner may seq scan)
SELECT * FROM orders WHERE status = 'active';

-- Good: index aligned with the predicate
CREATE INDEX idx_orders_status ON orders (status);
```

### Avoid SELECT *

Fetch only columns the application needs — less I/O, memory, and network.

```sql
-- Avoid
SELECT * FROM users WHERE id = 1;

-- Prefer
SELECT id, name, email FROM users WHERE id = 1;
```

### Use LIMIT (and real pagination)

Do not pull millions of rows when the UI needs a page.

```sql
-- Bad habit for huge tables
SELECT * FROM logs ORDER BY created_at DESC;

-- Page explicitly (OFFSET has limits at scale; keyset pagination is often better)
SELECT * FROM logs ORDER BY created_at DESC LIMIT 20 OFFSET 0;
```

### Avoid functions on indexed columns

Wrapping a column in a function often **blocks** a plain index on that column. Move the expression to the **value** side or use a **functional** index if the pattern is fixed.

```sql
-- Often cannot use a normal index on created_at
SELECT * FROM events WHERE YEAR(created_at) = 2024;

-- Range on the column uses a btree index
SELECT * FROM events
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

## Key takeaways

<SummaryBox title="Query optimization — recap">
- **EXPLAIN** (and **ANALYZE** where available) **before** you optimize — prove where time and rows go.
- **Index** columns used in **WHERE**, **JOIN**, and **ORDER BY**; understand **composite** and **prefix** rules.
- Prefer **narrow SELECT lists**, **LIMIT** / **pagination**, and **keyset** patterns for large tables at scale.
- Do not wrap **indexed columns** in arbitrary **functions** unless you add matching **functional** indexes.
- Kill **N+1** access with **joins** or **batched** loads; watch **OR** and **leading-wildcard LIKE** for plan regressions.
</SummaryBox>
