# Redis vs Memcached

**Redis** and **Memcached** are both **in-memory** systems used heavily for **caching**. The choice is less about “which is faster in the abstract” and more about **features**, **operations**, and **access patterns**. Memcached optimizes for **simple opaque blobs**; Redis adds **data structures**, **persistence**, and **broader ecosystem**.

<Callout variant="tip" title="Interview framing">
“Memcached vs Redis” is usually **features vs simplicity**. For **only** caching serialized pages or DB rows as blobs, Memcached remains credible. For **sessions, rate limits, rankings, queues-lite**, Redis wins on **expressiveness** — not always raw single-thread vs multi-thread in isolation.
</Callout>

## Key takeaways

<SummaryBox title="Redis vs Memcached — recap">
- **Redis**: **data structures**, **persistence**, **replication**, **pub/sub**, **ecosystem** — default choice when the cache is also a **mini datastore**.
- **Memcached**: **minimal** model, **multi-threaded** server, **memory-efficient** for **opaque** values — great when you only need a **distributed hash table**.
- For **simple caching only**, Memcached can be **competitive** on **throughput per box**; measure with **your** value sizes and **hot key** layout.
- For **anything beyond** blob cache (structures, HA, durability options), **Redis** is usually the **better fit**.
- Many **greenfield** stacks pick **Redis** for **versatility** and **managed offerings** (ElastiCache supports both — compare SKUs and limits).
</SummaryBox>
