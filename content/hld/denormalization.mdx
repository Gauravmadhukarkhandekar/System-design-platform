# Denormalization

**Denormalization** means **intentionally storing redundant data** so hot reads avoid **JOINs** and extra round-trips. It is the **mirror** of classical **normalization**: you trade **storage and update discipline** for **read latency** and **simpler query shapes** — common in **read-heavy**, **large-scale** systems once you have **evidence** of pain.

## What is denormalization?

**Normalization** splits facts into tables and uses **foreign keys** to avoid repeating the same data. **Denormalization** **copies** or **embeds** data so a read path can satisfy a screen or API **without joining** many large tables.

## Common techniques

  title="Patterns you will see in production"
  columns={['Technique', 'Idea', 'Example']}
  compact

    [

      'Store a slice of another entity on the row you read most.',

    [
      'Pre-compute aggregates',
      'Persist counts, sums, or ratings updated on write or on a schedule.',
      'products.review_count maintained by triggers, app logic, or stream consumers instead of COUNT(*) on every product page.',
    ],
    [
      'Duplicate across tables',
      'Copy hot columns into a second table shaped for a specific query.',
      'posts.author_display_name duplicated from users.display_name for feed rendering.',
    ],
    [
      'Materialized views',
      'Store the result of a heavy query as a table (refreshed periodically or on demand).',
      'Warehouse or Postgres-style materialized snapshot used for dashboards; OLTP may use similar ideas with explicit tables.',
    ],
  ]}
/>

```sql
-- Illustrative: refresh strategy is engine-specific
CREATE MATERIALIZED VIEW sales_summary AS
SELECT date_trunc('day', created_at) AS day, SUM(amount) AS revenue
FROM orders
GROUP BY 1;

-- Postgres: REFRESH MATERIALIZED VIEW sales_summary;
```

<Callout variant="warning" title="Do not denormalize by default">
Start **normalized**, **measure** (slow queries, lock waits, replica lag), then **denormalize targeted hot paths**. Premature duplication spreads bugs: inconsistent names, wrong aggregates, and painful migrations.
</Callout>

## Key takeaways

<SummaryBox title="Denormalization — recap">
- Denormalization **trades** write and consistency **complexity** for **read performance** and **simpler** access paths.
- It **reduces JOINs** by **duplicating** or **embedding** data where reads happen.
- It fits **read-heavy**, **write-light** shapes best — especially when **change frequency** on copied fields is low.
- You need a **plan** for **updates**: synchronous multi-table writes, **jobs**, **CDC**, or **eventual** reconciliation.
- **Measure first** — only denormalize **proven** bottlenecks; keep a **clear source of truth** for each fact.
</SummaryBox>
